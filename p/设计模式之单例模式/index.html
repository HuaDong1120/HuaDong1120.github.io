设计模式之单例模式

2026-04-05

一，单例模式到底解决什么问题

单例模式(Singleton Pattern)属于创建型模式，它的核心约束只有一条：一个类在整个程序的生命周期中只能有一个实例，且提供全局访问点。

典型场景

配置管理器、日志系统、线程池、资源管理器，这些组件在语义上应当全局唯一，用单例合理。

二，四种常见写法与各自缺陷

1，饿汉式（程序启动即创建)

// 饿汉式：类加载时就初始化
class Singleton {
public:
    static Singleton& getInstance() {
        return instance;
    }
private:
    Singleton() = default;
    static Singleton instance;  // 静态实例
};
Singleton Singleton::instance;

优点：天然线程安全，实现简单。 缺点：不支持延迟初始化，程序启动即创建；构造失败难处理。

2，懒汉式（首次访问时创建）

问题：多线程下，两个线程同时通过nullptr检查，会创建两个实例。

3，加锁版懒汉式

static Singleton* getInstance() {
    std::lock_guard<std::mutex> lock(mtx);
    if (instance == nullptr) {

线程安全了，但是每次调用getInstance都要竞争锁，高频访问下性能损耗明显-锁是性能消耗大户，多线程都是追求无锁化，进行优化程序。

4，双重检查锁(DCLP)

static Singleton* getInstance() {
    if (instance == nullptr) {         // 第一次检查（无锁）
        std::lock_guard<std::mutex> lock(mtx);
        if (instance == nullptr) {     // 第二次检查（有锁）
            instance = new Singleton();
        }
    }
    return instance;
}

C++11 之前是未定义行为

new Singleton() 在底层分三步：分配内存 → 调用构造函数 → 赋值给指针。编译器和 CPU 可能将赋值重排到构造函数之前，导致另一线程拿到未构造完成的对象。需要 std::atomic + 显式内存序才能修复，代码复杂度急剧上升。

三，我认为最优的实现:Meyers’ Singleton

Scott Meyers 在《Effective C++》中推荐的写法，利用 C++11 标准保证的"函数局部静态变量初始化是线程安全的"这一特性：

class Logger {
public:
    static Logger& getInstance() {
        static Logger instance;   // C++11 保证此处线程安全
        return instance;
    }

    void log(const std::string& msg) {
        // ... 日志逻辑
    }

    // 删除拷贝和移动，彻底封死复制路径
    Logger(const Logger&) = delete;
    Logger& operator=(const Logger&) = delete;
    Logger(Logger&&) = delete;
    Logger& operator=(Logger&&) = delete;

private:
    Logger() { /* 初始化 */ }
    ~Logger() { /* 清理 */ }
};

为什么这个写法好

局部静态变量在 C++11 中明确规定：若多个线程竞争初始化同一静态局部变量，只有一个线程执行初始化，其余线程等待完成。无需任何锁，延迟初始化，析构顺序由运行时保证（LIFO），没有内存泄漏。

四，线程安全的深层讨论

有一个常见误解需要澄清：Meyers’ Singleton 保证的是初始化的线程安全，不是使用的线程安全。

如果 Logger::log() 内部修改了成员变量，多线程并发调用仍然需要在方法内部加锁。单例模式只解决"创建唯一实例"的问题，不自动让整个对象变成线程安全的。

#pragma once
#include <type_traits>

/**
 * @brief CRTP 单例基类模板
 *
 * 用法：
 *   class MyManager : public Singleton<MyManager> {
 *       friend class Singleton<MyManager>;  // 允许访问私有构造函数
 *   private:
 *       MyManager() = default;
 *   public:
 *       void doSomething();
 *   };
 *
 *   auto& mgr = MyManager::getInstance();
 */
template <typename T>
class Singleton {
public:
    /// 获取单例引用（线程安全，C++11 保证）
    static T& getInstance() {
        static T instance;
        return instance;
    }

    // 禁止拷贝和移动
    Singleton(const Singleton&)            = delete;
    Singleton& operator=(const Singleton&) = delete;
    Singleton(Singleton&&)               = delete;
    Singleton& operator=(Singleton&&)    = delete;

protected:
    // protected 构造/析构：只允许子类调用
    Singleton()  = default;
    ~Singleton() = default;
};

class ConfigManager : public Singleton<ConfigManager> {
    // 步骤一：声明 friend，让基类能访问私有构造函数
    friend class Singleton<ConfigManager>;

private:
    // 步骤二：构造函数设为 private
    ConfigManager() {
        loadFromFile("config.ini");
    }

public:
    // 步骤三：正常写业务方法
    std::string get(const std::string& key) const;
    void set(const std::string& key, const std::string& val);
private:
    void loadFromFile(const std::string& path);
    std::map<std::string, std::string> data;
};

// 调用方式
auto& cfg = ConfigManager::getInstance();
cfg.set("theme", "dark");
std::string theme = cfg.get("theme");

构造/析构放在 protected 而非 private，是为了让派生类的构造函数能正常调用基类；同时 delete 掉所有拷贝和移动操作，从类型系统层面杜绝意外复制。friend 声明则是为了让 static T instance 的构造能访问子类的私有构造函数——这是 CRTP 单例的标准配方。

六，总结一下选择策略：

如果你的项目是 C++11 及以上，直接用 Meyers’ Singleton（局部静态变量）——简单、安全、零额外依赖。如果你有多个类需要单例化，引入 CRTP 模板基类，让继承代替重复代码。无论哪种方式，都要牢记：单例保证的是唯一性，业务方法的线程安全需要你自己负责。
